Close the OpenSpec change: $ARGUMENTS

Language: this command is written in English, but serve the user in THEIR language (French by default when their request is in French).

## Sequence

1. **Tasks.** For each task of `openspec/changes/<change>/tasks.md`: tick it only if the suite it names passes now (targeted run of that suite). Otherwise leave it unticked and write the reason "(pas de test : …)" given by the user (a user step, a manual check). Never tick on your own judgement.
2. **Status documents.** Update the status documents the repository keeps, when there are any (a status line at the top of a design document); when there is none, write nothing and create no entry.
3. **History.** CHANGELOG.md is frozen: add no entry; the milestone's closed features feed the release notes.
4. **Sync.** Find the feature whose `change` is this change: take the identifier `R-<n>` cited in the change's `proposal.md` or `tasks.md`. Read the queue first: `uv run tools/gh_issue.py list --sortie <file in the scratchpad folder>`; stop on any non-zero code and report its line. Then run `uv run --with pyyaml python tools/roadmap.py show <id> --issues-json <that file>` and check that its `change :` line is this change. If no identifier is cited or the line differs, ask the user for the identifier and write nothing to GitHub: never invent a feature. Otherwise run `uv run tools/gh_issue.py sync-tasks <id>` now, before the archive (the tool refuses an archived change); the write is approved by the user at the permission prompt. On exit code 8 (state unknown): stop, show the check command the tool printed, make no further GitHub write until the user has checked, and never say the write was not sent.
5. **Archive.** Only if every unticked task carries a reason AND the user confirms: archive with the OpenSpec archive command. If an unticked task has no reason, do not archive and name the task.
6. **Close the feature.** After the archive, before closing the feature, list the paths changed on the branch since its merge base with `main` (`git diff --name-only main...HEAD`, which compares against that merge base) and check them against the include and template rules of `edition/manifest.yaml`. When at least one changed path enters the edition, name those paths, propose the label `edition:public` and pass `--edition-public` to `close-feature` only after the user's yes; the tool adds the label before closing. Otherwise say that no path of the edition changed and pass no option. Then run `uv run tools/gh_issue.py close-feature <id>` (approved at the permission prompt). When user-step sub-issues remain open, the feature stays `In progress`: list them. List the features the closure unblocks, for the user to set `Ready`. When an agent sub-issue stays open and every unticked task of its group carries a reason, propose `uv run tools/gh_issue.py close-step <key> --reason "<reason>"` and run it only after the user's yes; the tool refuses an agent sub-issue without `--reason` (exit 7). Never propose it for a group with an unticked task without a reason: name that task. On exit code 8 from any of these commands: same stop as in step 4. Once `close-feature` has closed the feature (not when it stays `In progress`), check whether it was the last open feature of its milestone (the `jalon :` line of `roadmap.py show`): read the queue again, since the closure changed it: `uv run tools/gh_issue.py list --sortie <file in the scratchpad folder>` (on a non-zero code, report its line and say that the last-feature check could not be made, and do not run release-notes); then run `uv run --with pyyaml python tools/roadmap.py release-notes --milestone <milestone> --issues-json <that file>` in the foreground, without a pipe, and read its error output. Only when the command exits 0 and its error output holds neither `not listed: <n> open feature(s)` nor `GitHub unreachable`, add one line to your report: "Last open feature of <milestone>: run the weeding pass before the release (inventory kept in the lab folder, outside the repository)." When the output holds `GitHub unreachable` or the command fails, say that the last-feature check could not be made. Otherwise add nothing. (This check replaces nothing; removal: none, permanent, because the weeding happens at every release.)
7. **Commit.** Stage files by name, run `uv run tools/identifiants_personnels.py` on them, run `bash tests/run_all.sh --staged` (no variable, no pipe, foreground), commit with `git commit` alone (no `NAME=value` before it) when green. Never set `PMZILLA_AFTER_COMMIT`; the variables a commit needs come from the session's environment (worktree script `tools/worktree.sh`). A test that needs the network and fails: stop and give the user the exact command for their Terminal, without a pipe.
8. **Hand over.** Print the finishing command for the user to type in the Terminal (the one-branch train, from the run tree): `bash ~/PMZilla-Lab/run/tools/finish_train.sh <branch>`. Never run it.

## Never

- Read or write GitHub other than through `tools/gh_issue.py`; use any `gh` command, a read included; pre-approve either in a header.
- Run the branch-finishing script (`tools/finish_train.sh`), push, or merge.
- Archive with an unticked task that has no reason.
- Use `--no-verify` or the owner bypass variable (`PMZILLA_SKIP_GREEN_CHECK`).
- Launch anything reserved to the user: the real Jira tools (`history_jira.py`, `export_jira_api.py`), `flow_import.py`, `flow_compare.py`, the indexer `pmzilla_lab_library.py` (`index`, `rename-collection`, `probe`, `status`), the database scripts (`db.py`, `db_backup.sh`, `db_up.sh`), any calculation with the database as source (`--source db`), any database client (`psql`, `docker exec`), the posture evaluation set.
- Read the content folders (`Bibliotheque-*`, `Watch-Lab`, `Watch-Excluded`), the sensitive files of `Flux-Lab/`, the database backups or the journal; write a person's, team's or project's name in any file.
